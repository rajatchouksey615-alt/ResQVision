# Candidate Intake and Police Assignment Decision Proposal

**Status:** Partially approved. The project owner approved the candidate-creation principle, Police-routing invariant, and organization-scoped reviewer-assignment authority on 2026-11-22. Remaining design choices in this proposal are not approved.
**Purpose:** Resolve the remaining architecture questions required before candidate intake and Police assignment implementation. This proposal maps to existing Open Architecture Decisions (OADs) and does not create new decision identifiers, change existing OAD statuses, or grant runtime permissions.

## Decision Context

The approved baseline requires that only a specifically assigned and authorized human Police reviewer with active membership in the candidate's Police organization can review it. Only a human reviewer records `VERIFIED`, `REJECTED`, or `FURTHER_REVIEW`; verified incident creation remains atomic and creates exactly one `OPEN` `AccidentIncident`. The broader baseline is recorded in the [domain governance decision register](domain_governance_decision_register.md) and [candidate review policy](../domain/candidate_review_verification_policy.md).

Code inspection confirms that authenticated event ingestion, exact event replay, candidate creation, Police organization membership, and verified incident creation each have reusable pieces. There is no candidate-to-Police binding, reviewer assignment, production AI authenticator, or `FURTHER_REVIEW` runtime path. Candidate API routes and `HasCandidateReviewPermission` remain fail-closed. See the [Candidate Intake and Police Assignment Architecture](../domain/candidate_intake_assignment_architecture.md) for the complete flow and code references.

## Runtime Compatibility and Required Changes After Approval

| Capability | Actual current behavior | Compatibility with recommendation |
|---|---|---|
| Event submission | API only writes a `DetectionEvent`; `AI_SERVICE_AUTHENTICATOR` is unset and the route fails closed. Ingestion checks source authorization/availability and same-key semantic replay. | Reuse event validation and idempotency. Configure approved machine credentials and enforce source-level grants before enabling. |
| Candidate creation | Internal `create_candidate` accepts an explicit event and is idempotent for an existing event link. Its machine branch bypasses the injected candidate policy; source availability is not rechecked there. | Do not expose this path unchanged. Route materialization through a dedicated policy-enforced service that checks source state, approved intake eligibility, Police routing, and audit atomically. |
| Police routing | Source has optional owner organization; candidate has no organization foreign key. | No existing relation is suitable as Police jurisdiction. Add an explicit source route and persist its candidate binding after approval. |
| Assignment | No candidate assignment model, command, route, or policy exists. | New assignment/history representation and exact-organization policy are required. Existing `ResponseAssignment` concerns incident response and is not reusable for reviewer assignment. |
| Review access | Candidate list/detail/review API views are unavailable; permission denies. The queue selector is not organization or assignment scoped. | Keep blocked until every operation uses assigned-user plus active exact-org membership checks. Do not enable a global Police queue. |
| `FURTHER_REVIEW` | Model choices contain only `VERIFIED` and `REJECTED`; candidate review is unique per candidate; review start rejects a second start. | Must change persistence and lifecycle before claiming full support. Existing verified/rejected transaction is compatible and reusable. |
| Audit | Safe action/context allowlists exist for event intake, candidate creation/start, and final decisions. No assignment or FURTHER_REVIEW actions exist. | Extend only after action/context semantics are approved; write with domain state in one transaction. |

## Readiness Decision

**Candidate verification is not ready for privileged end-to-end implementation.** Project-owner approval remains required for the AI authentication mechanism, event eligibility and cross-event duplicate policy, route-maintenance authority, reviewer cardinality/reassignment, and detailed `FURTHER_REVIEW` lifecycle. The candidate-creation principle, one-active-Police-route invariant, and scoped reviewer-assignment authority are already approved, but runtime controls and route/assignment records do not exist. Machine credential verification and audit implementation also need security/backend review. Existing exact-event idempotency and atomic verified-incident creation are reusable but do not implement the approved intake, routing, or assignment policies.

Until approvals are recorded and corresponding checks are implemented and verified, leave detection machine authentication unconfigured, candidate routes unavailable, and runtime permissions unchanged. The detailed readiness assessment is in [implementation readiness](../domain/implementation_readiness.md).
