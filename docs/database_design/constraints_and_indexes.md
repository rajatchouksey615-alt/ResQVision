# Database Constraints and Indexes

**Status:** PHASE_2_DESIGN_DRAFT — required integrity contract for the proposed schema. Constraints/indexes are not implemented.

This document is paired with the [schema specification](database_schema_specification.md) and [field dictionary](data_dictionary.md). Names below are proposed stable names for Django migrations. Application authorization and multi-row state transitions are not replaced by database constraints.

## Primary and Foreign Keys

- Every ResQVision-owned entity, join, and history row: `id uuid PRIMARY KEY`, generated by Django. Do not mix integer and UUID keys within domain tables.
- Django auth framework tables use configured framework defaults. Set `DEFAULT_AUTO_FIELD=BigAutoField` before their first migration if supported by the selected Django version; role FKs then use `bigint`.
- Foreign keys use explicit names and a deliberate `on_delete` policy. Retained domain references use `PROTECT`/PostgreSQL `RESTRICT`; user actor references may use `SET_NULL` only when the actor UUID snapshot remains. Avoid cascading deletion through source events, candidates, incidents, assignments, review, evidence, histories, notifications, and audits.
- All FK IDs are non-null unless an association is intentionally optional and protected by a row check. Django creates FK indexes by default. When the leading columns of an existing full/composite index or unique constraint serve the same lookup, set that FK's `db_index=False` to avoid a duplicate; do not assume an index with the FK in a later column or a narrow partial predicate replaces the FK index.

## Check Constraints

Use named PostgreSQL `CHECK` constraints for rules over the current row. The following expressions are conceptual SQL fragments for later migrations, not executable migration code.

| Name | Table | Rule |
|---|---|---|
| `ck_user_email_canonical` | User | `email = lower(btrim(email)) AND length(email) > 0`; validate syntax/normalization in Django as well. |
| `ck_org_kind` | Organization | Kind is `POLICE`, `HOSPITAL`, `SOURCE_OWNER`, or `OTHER`; `code` and `display_name` are non-blank. |
| `ck_membership_status` | OrganizationMembership | Status is `ACTIVE`, `SUSPENDED`, or `REVOKED`. Role group names and organization-kind compatibility are checked by backend because they span rows. |
| `ck_source_type` | VideoSource | Source type is `CONTROLLED_FILE`, `CAMERA_STREAM`, or `OTHER`. |
| `ck_source_states` | VideoSource | Authorization and availability values are from the declared dictionaries. If `AUTHORIZED`, `authorized_by_user_id` and `authorized_at` are both non-null; these are both null otherwise unless policy retains prior approval on suspension/revocation. Prefer keeping approval audit in AuditEvent and clearing current approval fields on revoke. |
| `ck_source_owner_ref` | VideoSource | At least one of `owner_organization_id` or non-blank `owner_external_ref` is present. |
| `ck_event_outcome` | DetectionEvent | Processing outcome is `OBSERVATION` or `UNCERTAIN`; a no-observation result or processing failure does not create a DetectionEvent row. |
| `ck_event_confidence` | DetectionEvent | `confidence IS NULL OR confidence BETWEEN 0 AND 1`. |
| `ck_event_digest` | DetectionEvent | Optional digest is exactly 64 lowercase hexadecimal characters. |
| `ck_candidate_status` | Candidate | Status is `RECEIVED`, `UNDER_REVIEW`, `VERIFIED`, or `REJECTED`. |
| `ck_association_method` | CandidateDetectionEvent | Method is `RULE_BASED`, `REVIEWER_CONFIRMED`, or `MANUAL`; manual methods require a user actor. |
| `ck_review_rationale` | CandidateReview | `decision` is `VERIFIED` or `REJECTED`; rejection requires `NULLIF(btrim(rationale), '') IS NOT NULL`. A normal unique constraint on non-null `candidate_id` permits only one final decision under the no-reopen MVP rule. |
| `ck_incident_status` | Incident | Status is `OPEN`, `RESPONSE_ACTIVE`, `RESOLVED`, or `CLOSED`. |
| `ck_evidence_creator` | EvidenceAsset | Exactly one of `created_by_user_id`, `created_by_service_ref` is non-null. |
| `ck_evidence_size` | EvidenceAsset | `size_bytes IS NULL OR size_bytes > 0`. |
| `ck_evidence_checksum` | EvidenceAsset | Optional SHA-256 value matches `^[0-9a-f]{64}$`. |
| `ck_evidence_state` | EvidenceAsset | Status is one of the declared evidence states; scan status is `PENDING`, `NOT_REQUIRED`, `PASSED`, or `FAILED`. `AVAILABLE` requires media type, positive size, checksum, `validation_completed_at`, and scan state `NOT_REQUIRED` or `PASSED`. `DELETED` requires `deleted_at`; `EXPIRED` requires `expired_at`. |
| `ck_evidence_target_xor` | EvidenceAssociation | Exactly one target is set: `num_nonnulls(video_source_id, candidate_id, incident_id) = 1`. |
| `ck_upload_time_order` | EvidenceUploadSession | `expires_at > created_at`; if authorized, `authorized_at` is present; if completed, `completed_at` is present. Upload session state is in its declared allow-list. |
| `ck_location_subject_xor` | LocationRecord | Exactly one subject FK is set: `num_nonnulls(subject_video_source_id, subject_candidate_id, subject_incident_id) = 1`. |
| `ck_location_claim_subject` | LocationRecord | `CAMERA_POSITION` requires a VideoSource subject; `ACCIDENT_LOCATION` requires a Candidate or Incident subject. |
| `ck_location_vocabularies` | LocationRecord | `claim_kind` is `CAMERA_POSITION` or `ACCIDENT_LOCATION`; `source_method` is `CAMERA`, `GPS`, `INFERRED`, or `MANUAL`; verification status is `UNVERIFIED`, `VERIFIED`, or `CORRECTED`. |
| `ck_location_coordinate_pair` | LocationRecord | Both latitude/longitude are null, or both are present and in range: latitude `BETWEEN -90 AND 90`, longitude `BETWEEN -180 AND 180`. |
| `ck_location_accuracy` | LocationRecord | `accuracy_m IS NULL OR accuracy_m >= 0`. |
| `ck_location_verified_pair` | LocationRecord | `verified_by_user_id` and `verified_at` are paired; both are required for `VERIFIED` or `CORRECTED`, and both are null for `UNVERIFIED`. |
| `ck_location_creator_xor` | LocationRecord | Exactly one of human creator and non-secret service creator is set. |
| `ck_correction_coordinate_pairs` | LocationCorrectionHistory | Previous and new latitude/longitude values are each null as a pair or within the same coordinate ranges; accuracy values are null or non-negative. |
| `ck_correction_reason` | LocationCorrectionHistory | `NULLIF(btrim(reason), '') IS NOT NULL`. |
| `ck_assignment_status` | ResponseAssignment | Status is `PENDING`, `ACKNOWLEDGED`, `IN_PROGRESS`, `COMPLETED`, `UNABLE_TO_RESPOND`, `CANCELLED`, or `EXPIRED`. |
| `ck_asg_replace_not_self` | ResponseAssignment | `replacement_for_id IS NULL OR replacement_for_id <> id`; same-incident and prior-cancelled rules are transactional domain checks. |
| `ck_response_activity_kind` | Response | Kind is in the declared simulated activity allow-list; details are bounded and must not contain patient/treatment data. |
| `ck_incident_history_transition` | IncidentStatusHistory | From/to states use the incident vocabulary; NULL from-state is permitted only for initial `OPEN`; resolver reason required for `RESOLVED`/`CLOSED`. |
| `ck_asg_hist_transition` | AssignmentStatusHistory | From/to states use the assignment vocabulary; NULL from-state is permitted only for initial `PENDING`; unable/cancel/expire transitions require a non-blank reason. |
| `ck_history_actor_xor` | Both status histories | Exactly one human actor FK or service reference is non-null. |
| `ck_notification_target_xor` | Notification | Exactly one of `incident_id`, `response_assignment_id` is set. |
| `ck_notification_status` | Notification | Status is `CREATED`, `PENDING`, `DELIVERED_SIMULATED`, `FAILED`, `READ`, or `CANCELLED`; `read_at` is present iff status is `READ`. |
| `ck_attempt_number` | NotificationDeliveryAttempt | `attempt_number > 0`; outcome is `DELIVERED_SIMULATED`, `FAILED`, or `CANCELLED`. |
| `ck_audit_actor_kind` | AuditEvent | `actor_kind=HUMAN` requires no service reference and either a human FK or non-blank actor snapshot; `actor_kind=MACHINE` requires a service reference, no human FK, and snapshot equal to that service reference; `actor_kind=ANONYMOUS` requires both actor FK/reference columns null and snapshot `ANONYMOUS`. Snapshot is always non-blank. |
| `ck_audit_target` | AuditEvent | `resource_type` is in the declared allow-list; `resource_id` may be null for authentication or an unaccepted ingestion attempt with no canonical target. |
| `ck_audit_outcome` | AuditEvent | Outcome is `SUCCESS`, `DENIED`, `FAILED`, or `SIMULATED`; context JSON is an object and allow-listed. |

Database CHECK constraints cannot validate other rows/tables. Do not attempt to enforce that a controlled-file VideoSource has an AVAILABLE source EvidenceAsset before authorization, that a candidate has one or more events before review, source authorization at event intake, candidate status versus review row, candidate-to-incident creation, organization-kind/group-name alignment, same-incident reassignment, or assignment-terminal aggregation with a cross-table CHECK. Use a transaction, row lock, FK/unique constraint, and explicit application/domain validation. The partial unique source-input index limits a controlled-file source to at most one source EvidenceAsset; the minimum/availability rule is transactional.

Do not add a GIN index for auxiliary JSONB, a geospatial index, indexes on low-selectivity status alone, duplicate FK indexes already covered by a composite index, or indexes for hypothetical reporting. Recheck with `EXPLAIN (ANALYZE, BUFFERS)` against representative approved data after implementation. Partitioning, BRIN indexes for large append-only tables, and concurrent index builds are future scale decisions; no volume assumption is fabricated.

## Django Mapping Notes

- Model `UniqueConstraint`/`CheckConstraint` names explicitly; use conditional unique constraints for partial indexes only after confirming the selected Django/PostgreSQL versions support them. PostgreSQL conditional unique constraints are backed by unique indexes rather than ordinary table constraints.
- Ensure migrations create matching type lengths, nullability, constraint predicates, and FK `on_delete` behavior. Do not rely only on `Model.clean()` because it is not applied on every save path.
- Keep state transition validation in domain services and transactions. A `CHECK(status IN (...))` validates vocabulary, not transition history.
- Review generated SQL before applying migrations; use `SeparateDatabaseAndState` or custom operations only if Django's model state cannot faithfully describe the intended PostgreSQL index/constraint.
