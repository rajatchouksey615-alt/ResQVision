# Database Constraints and Indexes

**Status:** Database integrity contract synchronized with the implemented Django migrations. Retention, authority, and transaction policies remain subject to review.

This document is paired with the [schema specification](database_schema_specification.md) and [field dictionary](data_dictionary.md). Names below match the current Django migrations unless explicitly identified as a domain-layer rule. Application authorization and multi-row state transitions are not replaced by database constraints.

## Primary and Foreign Keys

- Every ResQVision-owned entity, join, and history row: `id uuid PRIMARY KEY`, generated by Django. Do not mix integer and UUID keys within domain tables.
- Django auth Group and Permission use `integer` keys in Django 5.2.19 migrations. `DEFAULT_AUTO_FIELD=BigAutoField` applies to project models without explicit keys; `organizations_membership.role_group_id` is `integer` to match `auth_group.id`.
- Foreign keys use explicit names and a deliberate `on_delete` policy. Retained domain references use `PROTECT`/PostgreSQL `RESTRICT`; user actor references may use `SET_NULL` only when the actor UUID snapshot remains. Avoid cascading deletion through source events, candidates, incidents, assignments, review, evidence, histories, notifications, and audits.
- All FK IDs are non-null unless an association is intentionally optional and protected by a row check. Django creates FK indexes by default. When the leading columns of an existing full/composite index or unique constraint serve the same lookup, set that FK's `db_index=False` to avoid a duplicate; do not assume an index with the FK in a later column or a narrow partial predicate replaces the FK index.

Database CHECK constraints cannot validate other rows/tables. Do not attempt to enforce that a controlled-file VideoSource has an AVAILABLE source EvidenceAsset before authorization, that a candidate has one or more events before review, source authorization at event intake, candidate status versus review row, candidate-to-incident creation, organization-kind/group-name alignment, same-incident/prior-cancelled reassignment, or assignment-terminal aggregation with a cross-table CHECK. Use a transaction, row lock, FK/unique constraint, and explicit application/domain validation. The partial unique source-input index limits a controlled-file source to at most one source EvidenceAsset; the minimum/availability rule is transactional.

Do not add a GIN index for auxiliary JSONB, a geospatial index, indexes on low-selectivity status alone, duplicate FK indexes already covered by a composite index, or indexes for hypothetical reporting. Recheck with `EXPLAIN (ANALYZE, BUFFERS)` against representative approved data after implementation. Partitioning, BRIN indexes for large append-only tables, and concurrent index builds are future scale decisions; no volume assumption is fabricated.

## Django Mapping Notes

- Model `UniqueConstraint`/`CheckConstraint` names explicitly; use conditional unique constraints for partial indexes only after confirming the selected Django/PostgreSQL versions support them. PostgreSQL conditional unique constraints are backed by unique indexes rather than ordinary table constraints.
- Ensure migrations create matching type lengths, nullability, constraint predicates, and FK `on_delete` behavior. Do not rely only on `Model.clean()` because it is not applied on every save path.
- Keep state transition validation in domain services and transactions. A `CHECK(status IN (...))` validates vocabulary, not transition history.
- Review generated SQL before applying migrations; use `SeparateDatabaseAndState` or custom operations only if Django's model state cannot faithfully describe the intended PostgreSQL index/constraint.
