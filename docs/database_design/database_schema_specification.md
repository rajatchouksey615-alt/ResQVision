# PostgreSQL Database Schema Specification

**Status:** Physical schema specification synchronized with Django model/migration state. Migrations have been applied only to the isolated local development database.

## Design Decisions

| Decision | Recommendation | Rationale and boundary |
|---|---|---|
| Primary keys | Native PostgreSQL `uuid`, generated by Django with Python `uuid.uuid4` for every ResQVision-owned row, including association and history rows. Django auth Group/Permission and framework-owned tables retain their migration-defined integer keys. | One consistent identifier type across application domains; safe as opaque API identifiers; event idempotency still uses its business key. No PostgreSQL extension is required. |
| Human account model | Define a custom Django `AbstractUser` subclass before the first migration; remove the inherited `username` field and use normalized unique email as `USERNAME_FIELD`, with a custom manager. | Django documents that `AUTH_USER_MODEL` should be selected before initial migrations; changing it later is difficult. Keep domain fields out of the auth table. |
| Role | Django built-in `Group`/`Permission`, not a parallel custom Role table | `ADMIN`, `POLICE`, and `HOSPITAL` are seeded group codes. Multiple groups per user are supported. OrganizationMembership supplies the required Police/Hospital object scope. `AI_SERVICE` remains an external machine principal. |
| Organization scope | `Organization` plus `OrganizationMembership(user, organization, role_group)` | One human can hold multiple roles and memberships. Police/Hospital access requires an active membership in the target organization in addition to the group permission. Admin is a global group and every privileged action remains audited. |
| Status storage | `varchar` with named `CHECK` constraints, mapped to Django `TextChoices` in a later implementation | Avoids PostgreSQL enum alteration friction while constraining stored values. Cross-row transition rules remain in backend transactions. |
| Timestamps | `timestamptz`; application sets Django `USE_TZ=True`; all instants are written/read in UTC | Preserves unambiguous instants. Client display converts to local time; source-local time zones are not inferred. |
| Coordinates | `numeric(9,6)` latitude/longitude and nullable `numeric(10,2)` accuracy in metres | Range is constrained; coordinate scale does not assert measurement accuracy. Accuracy/uncertainty is separate and may be unknown. No PostGIS extension is proposed for MVP. |
| Flexible metadata | Use `jsonb` only for versioned AI-specific auxiliary metadata and allow-listed, non-sensitive audit context | Identity, state, relationships, timestamps, and query-critical fields remain relational. Validate JSON shape/version in application code; do not put core fields in JSONB. |
| Evidence bytes | Object storage; PostgreSQL stores opaque object namespace/key and metadata only | Never persist media bytes, public URLs, signed URLs, or storage credentials in domain rows. Provider remains an approval decision. |
| Audit reference | `resource_type` constrained to a fixed code set plus `resource_id uuid` | The sole deliberate cross-domain generic reference, because one append-only audit ledger spans many unrelated tables. It is not a business relation and is not used in place of normal foreign keys. |

### UUID versus BigAutoField

`BigAutoField` is compact and conventional for a single relational database, but UUIDs are selected for all ResQVision-owned domain rows because identifiers cross service, upload, and audit boundaries and should be opaque references. PostgreSQL stores UUID natively. The academic workload does not justify mixed domain identifiers or UUIDv7/version-specific behavior. Django generates UUIDv4 at the application boundary, so no database extension or server-side generator is required. The configured `DEFAULT_AUTO_FIELD=BigAutoField` applies to project models without an explicit key; Django 5.2.19's historical auth migrations still define `auth_group` and `auth_permission` keys as `AutoField` (`integer`). The membership FK therefore correctly uses `integer`, not `bigint`.

### User and Role Boundary

Use `settings.AUTH_USER_MODEL` for every application FK. An `AbstractUser`-based custom model is preferred over a separate domain User table; remove `username`, define a custom manager, set `USERNAME_FIELD='email'`, and keep email, authentication flags, Django's password hash, and standard auth relations there. Normalize email to trimmed lowercase before validation and persistence, require a unique value, and retain Django's password hashing/validation. Disabling `is_active` blocks login; revoke memberships and role grants as part of offboarding. Ordinary account deletion is deactivation and, where approved, anonymization while retained relationships/history remain. Password reset tokens, JWTs, refresh tokens, camera credentials, storage credentials, and service secrets are not stored in ordinary domain tables. If refresh-token revocation becomes a requirement, design a separate hashed-token record with expiry and rotation rules before implementation.

Represent `Role` through Django `Group` and `Permission`; do not create a duplicate role table. A user may hold multiple roles; `ADMIN` is global, while Police/Hospital group membership must also match an active OrganizationMembership for the target organization. A user may belong to multiple organizations. Authorization checks combine the role capability and target scope; the backend must not rely on client role claims alone. A unique group-name convention (`ADMIN`, `POLICE`, `HOSPITAL`) is seeded in a controlled data migration. Role/group creation, mapping, and changes are privileged and audited. Do not use Django's per-user permission M2M for ordinary application grants. `is_staff` controls Django admin-site access and is not an application role; `is_superuser` bypasses Django permissions and is restricted to tightly controlled administration, never silently treated as an ordinary ResQVision role.

`AI_SERVICE` is not a human User, Django Group, or OrganizationMembership. Authentication credentials live in a secret manager/runtime configuration. The database may retain a non-secret stable service principal reference in an event/audit row for attribution; it must never contain the credential itself.

## State and Integrity Ownership

- Current `status` is stored on Candidate, Incident, Assignment, EvidenceAsset, UploadSession, Notification, VideoSource authorization/availability, and membership. Corresponding history tables or AuditEvent are append-only evidence of changes, written in the same transaction as current-state updates. They do not replace each other or merge different lifecycle owners.
- CandidateReview records the single final human decision, while Candidate.status is the queryable current state. A unique constraint permits at most one final decision per candidate under the MVP no-reopen rule. A future correction/reopen policy needs a reviewed schema change.
- AccidentIncident has a non-null unique candidate FK. It cannot exist without a verified candidate, and the backend creates it in the verification transaction.
- ResponseAssignment has its own target and status; no shared Police/Hospital status field exists. Assignment histories and incident histories are separate.
- Response is activity detail, not another current assignment status. AssignmentStatusHistory is the authoritative transition log.
- Notification and delivery attempts are simulation-only; notification state is never authoritative for incident or response state.
- `AVAILABLE` EvidenceAsset means the opaque object reference, size, SHA-256, and validation completion are recorded and any required content scan passed. Only the backend grants retrieval. Controlled-file VideoSources use a source-level EvidenceAssociation to a private source-video EvidenceAsset; live camera configuration stays outside ordinary domain tables.
- AuditEvent is append-only for the ordinary application database role. Human attribution uses a nullable user FK plus a non-secret actor snapshot so approved identity erasure can remove the direct FK without rewriting history; machine attribution uses a stable non-secret service reference; unauthenticated attempts use an `ANONYMOUS` actor kind without retaining submitted identifiers.
- All values controlled by the application are constrained both at the boundary and in PostgreSQL where row-local rules suffice. Transaction/domain code enforces cross-row transitions and authorization.

## Naming and Data-Type Conventions

- Use lowercase `snake_case` table/column names, explicit Django `db_table` only when stable names are useful, singular model names, and `*_id` FK column names.
- Use `uuid`, `boolean`, `smallint`/`integer` for bounded codes/counters, `bigint` for media bytes, `varchar(n)` for bounded identifiers/codes, `text` for longer rationale/details, `numeric(p,s)` for decimal measurements, `jsonb` only for the limited cases above, and `timestamptz` for instants.
- Do not store enum labels as PostgreSQL native ENUM in MVP. Constrain `varchar` status/code columns using named checks and centralize allowed values in a domain enum in future application code.
- Do not store local-time naive timestamps. Source time is an absolute instant when supplied; unknown timezone/clock quality is represented in provenance metadata, not guessed.
- Use `ON DELETE PROTECT`/`RESTRICT` for retained business relationships. Avoid `CASCADE` across incidents, assignments, evidence, review, and audit. User deactivation is the ordinary account lifecycle.

## Normalization and Read Model

- **First normal form:** Each column holds one value. Repeating events, evidence, memberships, assignments, activities, delivery attempts, and state transitions use child/join rows rather than lists or arrays. JSONB is limited to versioned auxiliary model metadata and allow-listed audit context; it does not contain relational identifiers or query-critical state.
- **Second normal form:** Associative facts are stored on explicit association rows and depend on their full business key. The schema uses UUID surrogate primary keys for implementation consistency, while unique constraints preserve natural idempotency/association keys such as `(video_source_id, external_event_id)` and `(user_id, organization_id, role_group_id)`.
- **Third normal form:** Organization kind, role grants, source authorization, candidate review, authoritative incident state, target assignment state, notification delivery, location provenance, and evidence metadata each have one owner. Police/Hospital state is not duplicated on Incident; notification outcome is not stored on assignment; object bytes are not copied into PostgreSQL; incident details are not copied into evidence or audit JSON.
- **History without update anomalies:** Current state stays on its owning entity for efficient queues and authorization; append-oriented history is written in the same transaction. That deliberate current-state/history duplication is a queryable current value plus its change log, not two independently writable sources of truth. CandidateReview is the one final decision record while Candidate.status mirrors its final state, atomically and under a no-reopen policy.
- **Location versioning:** LocationRecord keeps one current claim per typed subject with retained superseded rows. `is_current` and its partial unique index are a maintained current-head marker. Coordinate corrections have a before/after row; other provenance-field changes create a replacement claim.
- **Audit exception:** AuditEvent's constrained `(resource_type, resource_id)` is intentionally not a foreign key so one ledger can reference many unrelated domains. Every operational business relationship remains a typed FK.
- **No speculative aggregates:** Do not persist assignment counts, candidate event counts, notification read/ack flags on incidents, or derived response summaries. Compute them from their owning rows. If measured workloads later justify cached projections, keep them explicitly derived and rebuildable.

Indexes are selected for stated queues, per-entity timelines, scoped inboxes, idempotency, and retention/reconciliation scans. PostgreSQL B-tree/partial indexes and Django FK indexes cover the MVP access patterns; query plans should be checked with representative approved data before adding more. No GIN, spatial, partitioning, or BRIN design is assumed.

## Version and Implementation Preconditions

The local development compatibility baseline is Python 3.14.10, Django 5.2.19, Django REST Framework 3.18.3, Psycopg 3.3.9, and PostgreSQL 18.7. `AUTH_USER_MODEL`, UUID domain keys, `DEFAULT_AUTO_FIELD=BigAutoField`, and `USE_TZ=True` were set before the first migration. Migration SQL uses UUID, JSONB, check constraints, B-tree/partial indexes, and foreign keys; no PostGIS, extensions, custom SQL types, triggers, or stored procedures are required for the MVP schema. See the [transaction design](transaction_and_integrity_design.md), [retention design](data_lifecycle_and_retention.md), and [implementation plan](database_implementation_plan.md) for lifecycle and rollout details. Production compatibility and deployment remain to be reviewed before deployment.
