## Phase 2 Database Responsibility Traceability

This supplements the component/workflow matrix above with the database owner and integrity mechanism. The MVP schema and model constraints are implemented in Django migrations and covered by database tests; complete requirement behavior and cross-row service rules remain unimplemented.

| Requirement IDs | Database responsibility | Proposed tables and integrity design |
|---|---|---|
| FR-001, FR-002, NFR-001, NFR-003 | Human identity, normalized unique email, password hash responsibility, enabled state, and role grants | `accounts_user` custom Django user; Django `Group`/`Permission`; `uq_user_email`, canonical-email check; account disable/anonymization policy in lifecycle design. Tokens/secrets are excluded from domain tables. |
| FR-003, FR-028, NFR-023 | Registered source owner, authorization, availability, location, policy references, and authorization-at-intake guard | `organizations_organization`, `sources_video_source`, `locations_location_record`, `audit_audit_event`; source-code uniqueness, source-state/owner checks, source-row lock during intake. |
| FR-004, FR-007, FR-017, NFR-009 | Accepted observation provenance, source-scoped event identity, duplicate-safe retry, candidate provenance | `detection_detection_event`, `incidents_candidate_detection_event`; `uq_event_source_external`, `uq_candidate_event_once`, payload digest and ingestion transaction. No-observation/failure does not become an event row. |
| FR-005, FR-018, FR-019 | Candidate review state, final human decision, rejection retention, and single verified incident creation | `incidents_accident_candidate`, `incidents_candidate_review`, `incidents_accident_incident`, both status histories, `audit_audit_event`; reviewer check, unique final review, unique candidate-to-incident FK, atomic verification transaction. |
| FR-006, FR-025, FR-026, FR-027, NFR-006, NFR-022 | Private media metadata, typed source/candidate/incident association, scoped upload session, validation-before-availability, access/deletion audit | `evidence_evidence_asset`, `evidence_evidence_association`, `evidence_evidence_upload_session`; object-reference uniqueness, target XOR, checksum/size/state checks, external-storage reconciliation transaction. |
| FR-008, FR-011, FR-012, FR-020, FR-021, FR-023, FR-031, NFR-025 | Independent agency assignment lifecycle, target organization scope, activity and per-assignment history, reassignment, manual timeout default | `responses_response_assignment`, `responses_response`, `responses_assignment_status_history`, `organizations_membership`; active-target/command uniqueness, assignment transition transaction, incident-resolution guard. Police and Hospital state is never shared. |
| FR-009, FR-024, NFR-020 | Simulated notification and per-attempt outcomes, isolated from incident/assignment state | `notifications_notification`, `notifications_delivery_attempt`; target XOR, recipient/state/attempt indexes, independent creation and delivery transactions. No live emergency delivery. |
| FR-010, FR-029, NFR-024 | Distinct camera/accident location claims, source/time/accuracy, verification and correction attribution | `locations_location_record`, `locations_location_correction_history`; coordinate pair/range checks, current-claim partial unique indexes, append-oriented correction transaction. |
| FR-013, FR-014, FR-016, FR-030, NFR-008 | Privileged action attribution, state histories, scoped history reads, evidence-access audit, and protected audit ledger | `audit_audit_event`, `incidents_incident_status_history`, `responses_assignment_status_history`, plus domain history rows; actor-kind checks, append-only application DB grants, no secret payloads. |
| NFR-002, NFR-004, NFR-005, NFR-021 | Backend-only object authorization, machine identity separation, safe validation outcomes | User/Group/Membership and source/assignment/evidence FKs; `AI_SERVICE` remains a non-secret machine reference, with authorization enforced by Django domain services rather than client claims. |
| NFR-007, NFR-010, NFR-018 | Data minimization, retention, account deactivation, object-store/database reconciliation, and restore safety | Retention references on VideoSource/EvidenceAsset; explicit lifecycle rules and TBD durations in [lifecycle and retention](../database_design/data_lifecycle_and_retention.md); cross-system recovery in [transaction design](../database_design/transaction_and_integrity_design.md). |
| NFR-011, NFR-012, NFR-013, NFR-015, NFR-017, NFR-019 | Environment-dependent availability, performance, capacity, observability, compatibility, and AI evaluation | No numeric DB targets or scale assumptions are introduced. Select versions and workload before implementation; evaluate indexes with representative approved data in a later phase. |

## Traceability Notes

- The PostgreSQL-backed database model suite passes 50 tests. This does not claim that the functional requirements, APIs, or end-to-end workflows are complete.
- API schemas and concrete end-to-end test IDs are deferred until approved implementation contracts. Physical database fields and persistence checks are specified in the implemented [database design](../database_design/README.md).
- Requirements with team, institutional, or provider decisions remain REVISED_DRAFT and must be resolved or explicitly deferred before the related feature is implemented.
